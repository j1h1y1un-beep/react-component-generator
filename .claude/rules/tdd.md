# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **TDD를 적용한다.**

## RED - GREEN - REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 환경 문제로 인한 실패는 RED가 아니므로 고친 뒤 다시 실행한다.

### GREEN: 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 분기, 옵션을 넣지 않는다.
- **신규 테스트와 기존 테스트 전부** 통과하는지 실행해서 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 변경 후 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작이 남아 있으면 **RED로 돌아간다.**

## 삭제 강제

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- "참고용"으로 남겨두거나, 주석 처리하거나, 다른 파일에 옮겨두는 것도 **금지**다. 삭제는 삭제다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트가 불필요하다 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없는데 회귀를 막아준다. 단순해 보이는 코드에서 버그가 가장 자주 난다. |
| 나중에 테스트를 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰진다. 처음부터 통과하므로 아무것도 검증하지 못한다. 그리고 "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 RED-GREEN이 더 빠르다. |
| 이미 짠 코드를 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 삭제하고 테스트부터 다시 쓴다. |
| 프로토타입이다 | 프로토타입은 프로덕션이 된다. 버릴 코드라고 확신한다면 TDD 대상이 아니라 별도 브랜치에서 하고, 본 코드에는 TDD로 다시 구현한다. |
