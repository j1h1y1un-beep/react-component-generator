# Commit

변경사항을 분석해 컨벤션에 맞게 커밋하는 스킬이다. 별도의 사용자 승인 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 먼저 확인한다. 저장소가 아니면 커밋할 수 없다고 알리고 멈춘다(`git init`은 사용자가 요청할 때만).
- `git status --short`, `git diff`(unstaged), `git diff --cached`(staged)로 전체 변경을 파악한다.
- 최근 메시지 스타일은 `git log --oneline -10`으로 참고한다.
- 변경이 없으면 그렇게 알리고 끝낸다.

### 2. 논리적 단위로 분류
- 하나의 목적(기능 추가, 버그 수정, 리팩터링, 설정 변경 등)별로 변경을 묶는다. 서로 다른 목적이 섞여 있으면 커밋을 나눈다.
- 각 커밋에 포함할 파일(필요하면 hunk 단위)을 정한다. 테스트는 해당 기능과 같은 커밋에 둔다.
- 커밋하면 안 되는 파일은 제외하고 사용자에게 알린다.
  - `.env`, 키·토큰·인증서 등 비밀 값
  - `node_modules/`, `dist/` 같은 빌드·의존성 산출물
  - 변경 내용에 비밀 값이 들어 있으면 값은 출력하지 않고 파일명과 위치만 알린다.

### 3. 커밋 메시지 작성
형식은 다음과 같다.

```
<type>: <한국어 요약>

<필요한 경우 본문: 무엇을, 왜 바꿨는지>
```

- **type**
  - `feat`: 새 기능
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 빌드, 설정, 의존성, 기타 잡무
  - 필요하면 `docs`, `test`, `style`도 쓸 수 있다. 의미가 가장 가까운 type 하나만 고른다.
- 요약은 한국어로 50자 안팎, 마침표 없이, "~추가", "~수정", "~개선"처럼 간결하게 쓴다.
- 본문은 요약만으로 부족할 때만 쓰고, 변경 이유 위주로 적는다.
- 시스템에서 지정한 커밋 attribution 줄이 있으면 메시지 끝에 붙인다.

### 4. 커밋 실행
승인 단계 없이 바로 진행한다.

- 커밋마다 해당 파일만 `git add <파일>`로 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다.
- 여러 줄 메시지는 heredoc으로 전달한다.
- hook이 실패하면 원인을 고쳐 새 커밋을 만든다. `--no-verify`로 우회하거나 `--amend`로 덮어쓰지 않는다.
- 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인하고, 만든 커밋 목록(메시지, 포함 파일)과 제외한 파일·이유를 사용자에게 보고한다.

## 하지 말 것
- push하기. push는 별도로 요청받았을 때만 한다.
- 비밀 값이 든 파일을 커밋하기.
- 서로 무관한 변경을 한 커밋에 섞기.
